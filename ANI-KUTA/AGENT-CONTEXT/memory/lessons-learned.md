## How to Use

- **Trigger**: log an entry when (a) the user corrects you, OR (b) you catch your own mistake before/after continuing, OR (c) you have an insight worth remembering.
- **Format**: `- [TAG] lesson (source: <task-id or "self">, <YYYY-MM-DD>)`
- **Tags**: `MISTAKE` (you did wrong), `CORRECTION` (user fixed you), `INSIGHT` (realized), `PATTERN` (recurring).
- **Dedup**: grep existing entries for the keyword before adding. Don't log the same lesson twice.
- **Stale**: mark `~~strikethrough~~` with `→ superseded by <ref>` when a newer entry contradicts.
- **Promote**: if a lesson is a recurring `PATTERN`, also add a one-line rule to `CORE_RULES.md`.

- [PATTERN] For a floating overlay (sidebar, popover) that should close on tap-outside, place a transparent scrim `Box(Modifier.fillMaxSize().clickable { dismiss() })` as a sibling BEFORE the overlay in the parent `Box`. The scrim captures all taps on the parent area; the overlay (declared after the scrim) draws on top and consumes its own taps via `.clickable { /* consume */ }`. This is more reliable than putting `.clickable { dismiss() }` on the parent Box directly (which can interfere with child clickables) or on a sub-Box that doesn't cover the full area. - [PATTERN] Before merging a feature branch, always check if `main` has diverged: `git log --oneline feature..origin/main`. If the count is 0, the merge is a clean fast-forward (`git merge --ff-only`) — no merge commit, no conflict resolution needed. If main HAS diverged, a merge commit (or rebase) is needed and conflicts are possible. Always `git fetch origin main` first to get the latest remote state. The fast-forward-only flag (`--ff-only`) is a safety net: it aborts if a fast-forward isn't possible, preventing an accidental merge commit when you intended a fast-forward. (source: merge session, 2026-08-10)
- [PATTERN] Branch deletion order after a merge: (1) verify CI green on `main` FIRST (the merged code builds on the target branch), (2) delete the remote branch (`git push origin --delete <branch>`), (3) delete the local branch (`git branch -d <branch>` — the `-d` flag refuses to delete if the branch isn't fully merged, a safety net). Never delete the feature branch before CI on main is green — if main's build fails, you'd lose the ability to easily iterate on the feature branch. (source: merge session, 2026-08-10)
- [MISTAKE] Documentation can drift from code in TWO directions: (a) docs describe a state that was never built (e.g. `knowledge/architecture.md` proposed 8 modules + Room; actual 46 + SQLDelight — never updated after Phase 1), (b) docs describe a state that was REMOVED (e.g. 4 docs said "Nav3 on classpath unused" but Nav3 had been fully removed from all build files — the docs were stale by a full removal). - [MISTAKE] Enabling `PRAGMA foreign_keys = ON` (D-166) on a database with EXISTING data exposes EVERY latent FK violation that was silently dangling when FKs were OFF. Before enabling FK enforcement, audit EVERY FK in the schema: (a) is the parent table populated? (b) does the code actually insert parent rows before child rows? (c) does the code pass the correct parent ID (not a different-domain ID that happens to be a Long)? The D-189 crash was caused by `content.extension_id` having a FK to `content_ext(id)`, but `content_ext` was never populated + the code passed `source.id` (Aniyomi internal) as `extensionId` — a semantic mismatch that was invisible pre-D-166. RULE: when enabling FK enforcement on an existing schema, grep every FK column's write sites + verify the value being written is a real parent-row ID (not a different-domain ID). (source: D-189, 2026-08-12, FK enforcement crash on link-source)
- [PATTERN] When a lookup/parent table (like `content_ext`) has an `insertX`/`getOrCreateX` method but ZERO callers, the table is dead. Any FK referencing it from a populated table will crash once FK enforcement is ON. Two fixes: (a) wire up the table (call getOrCreate at every write site) — the "code matches schema" fix; (b) drop the FK (keep the column as a plain INTEGER) — the "schema matches code" fix. Choose (b) when the code has ALWAYS used a different ID domain (e.g. Aniyomi source.id vs content_ext.id) — the FK was wrong from the start. Choose (a) when the code is halfway-converted (some sites use the parent ID, some don't). The D-189 fix chose (b) because all 6 write sites consistently passed source.id. (source: D-189, 2026-08-12)
- [INSIGHT] SQLite `CREATE TABLE IF NOT EXISTS` does NOT alter an existing table's schema (it's a no-op if the table exists). This means schema changes to an existing table (adding/removing FK constraints, changing column types) do NOT take effect on existing installs — only on fresh installs (or after `DROP TABLE` + recreate). Per CORE_RULES §30 (debug = clear data / reinstall), this is acceptable for debug. For production, you need either `.sqm` migration files (SQLDelight) or an `onOpen` table-rebuild (CREATE new → INSERT SELECT → DROP old → RENAME). Don't assume editing the `.sq` file fixes existing installs — tell the user to reinstall. (source: D-189, 2026-08-12)
- [PATTERN] When building a multi-source metadata engine, use a pluggable provider interface with `supportedIdTypes: Set<ContentIdType>` rather than hardcoding the ID type. This makes the engine future-proof: adding a new ID type (e.g. TMDB) = a new provider module that declares its supported types — zero engine changes. The engine auto-selects providers based on the content's `ContentId.type`. D-190 used this pattern for AniZip (ANILIST+MAL) + Jikan (MAL) + Kitsu (ANILIST); a future TMDB provider would declare `{TMDB}`. (source: D-190, 2026-08-12)
- [PATTERN] When fetching from multiple providers in parallel with `coroutineScope { map { async { ... } }.awaitAll() }`, each `async` block MUST wrap its body in `try { ... } catch (e: Exception) { emptyMap() }`. Without per-async try/catch, one provider's exception propagates through `awaitAll()` → cancels the parent `coroutineScope` → all sibling in-flight providers are cancelled. This defeats the purpose of multi-source: you lose ALL data because ONE source failed. The pattern: `async { try { provider.fetch() } catch (e: Exception) { Logger.w(...); emptyMap() } }`. (source: D-190 sub-agent plan review, 2026-08-12)
- [INSIGHT] For boolean fields that come from only ONE source (e.g. `isFiller`/`isRecap` from Jikan only), use `Boolean?` (nullable) — NOT `Boolean = false`. Null means "unknown" (the source didn't report); false means "confirmed-not". If the source fails (network error, rate limit), the field stays null — UI shows no badge. If you default to false, the UI would show "non-filler" even though you don't actually know — misleading for long anime where Jikan pagination fails partway through. The merge strategy: OR-true across sources (if any says true, it's true; false-wins over null; null only if all null). (source: D-190, 2026-08-12)
