  stores, extension-prefs call sites, the debug-bubble DB tooling, `DATABASE.json` (parsed with

  (`lib/schema.ts`, `lib/databasePlan.ts`, `lib/databaseReview.ts`, `app/db-viewer`, `app/database`,

- Claims about code cite `file:line` and are `[verified]` unless marked `[inferred]`/`[gap]`.

**Headline findings** (each expanded later):

1. **24 tables in 16 `.sq` files**, single SQLDelight database `anikuta.db`, one `@Database`
   equivalent: `AnikutaDatabase` (`core/database/build.gradle.kts:10-16`). Koin singletons:
   `AnikutaApp.kt:240-241`.
2. **Identity = stable UUID `main_id` (PK) + mutable structured `content_id` string** generated by
   `ContentIdGenerator` — *not* "contentId = AniList id" (the brief's premise; see §2.1). AniList id
   lives in `content_details.data_source_ref_id` and is NULLABLE — CS3-only content is
   representable **today** at the row level.
3. **The real seam is `content_details`'s two-axis design** (`data_*` metadata axis vs `ext_*`
   extension axis, each independently linkable/unlinkable) + a seeded `system` lookup table that
   already contains a `cloudstream` row (`ContentRepository.kt:59-66`). BUT: the extension axis is
   **single-slot** (one extension link per content), and `main_entry.extension_id` is
   **INTEGER-typed** (Aniyomi Long source id) — two concrete blockers for CS3 (§8).
4. **Two different episode-key regimes coexist**: watch progress keys episodes
   `"${mainId}|%05d"` (normalized), downloads key them by `SEpisode.url` (source URL)
   (`DownloadModels.kt:52-58`). CS3's season-scoped episodes stress both (§8.2).
5. **Migration policy = none, deliberately** (CORE_RULES §30): no `.sqm` files, schema version
   pinned at 1, and a 250-line idempotent `onOpen` "make-sure-columns-exist" shim in
   `DatabaseDriverFactory` that is *not* a migration system (§7).
6. **`DATABASE.json` is a lossy device export** produced by the debug-bubble Database tab
   (`DebugDatabaseBrowser.exportAsJson()`, `DatabaseTab.kt:97-113`), manually uploaded by the user
   (root of worktree, 1.4 MB). It is a **pre-D-198 snapshot** — it still has the `content` /
   `anilist_detail` / `extension_detail` tables and lacks `main_entry` / `content_details` /
   `track_entry` / `playback_cache_entry` (§6.1). The dashboard's `lib/schema.ts` is **stale the
   same way** (shows 26 pre-D-198 tables; reality is 24) — violating CORE_RULES §25 (§6.4).
7. **Extension state lives entirely in SharedPreferences** (trust, enabled-set, repos, selected
   source, source links, aniyomi source prefs) — NOTHING extension-related is in SQLDelight except
   the seeded `system` lookup rows (§5).

## 1. Schema map — the complete table inventory

Single SQLite file `anikuta.db` (`DatabaseDriverFactory.kt:34`), FK enforcement ON via
`PRAGMA foreign_keys = ON` on every open (`DatabaseDriverFactory.kt:41`). 24 tables, grouped:

**The FK graph in one picture** (every `main_id` FK cascades on delete of the main_entry row —
deleting a content wipes its whole footprint):

```
                     ┌──────────────┐   data_source_id ──> data_source (4 rows, seeded)
                     │  main_entry  │──system_id ────────> system      (4 rows, seeded: aniyomi,
                     │ main_id UUID │                                        cloudstream, sora, mangayomi)
                     └──────┬───────┘
                            │ main_id, 1:1
                     ┌──────▼───────┐
                     │content_details│  (data_* axis ⇄ ext_* axis, both nullable)
                     └──────────────┘
  main_id referenced by (ALL ON DELETE CASCADE unless noted):
   library_item ──> library_category          watch_progress       activity_event (no FK)

   episode_schedule                           user_episode_rating  anime_update_state

   playback_cache_entry (NO FK — disposable cache, evicted not cascaded)
  Standalone: browse_cache, app_settings, data_source, system
```

## 2. Content identity system — the deep dive

### 2.1 The two-ID design: mainId (stable) + contentId (mutable, structured)

Every content gets a **`main_id` = random UUID assigned once, never changes**
(`ContentResolver.kt:13-14`, `:67`, `:157`). Every *user* table (library, watch, downloads,
ratings, notifications, schedule, updates, track, genres) FKs to `main_id` — so switching metadata
source or extension source **never orphans progress**. The `content_id` is a *diagnostic/overlap*
string that is regenerated on every source switch:

```
{dataSource}:{system}:{repoUrl|none}:{extensionPkg|none}:{sourceId|none}:{animeUrl|none}
```
(`ContentIdGenerator.kt:6-9`, generate at `:34-50`; D-135: full repo URL, not DB id, for
backup/restore). Real examples from `DATABASE.json`:
`"anilist:aniyomi:none:none:4697393375201558791:/watch/sakamoto-days-sfdxz"` and
`"none:aniyomi:none:none:7240671891085951555:the-seven-heavenly-virtues-o0omp"`.
It is explicitly "NOT shown in the UI — internal tracking only" (`ContentIdGenerator.kt:17-18`) and
is the **reinstall-recognition key** for downloads: `data.json` carries `contentId` because
"mainId is a random UUID that changes on reinstall" (`ContentDataJson.kt:24-27`).

**So the brief's premise "contentId = AniList id" is wrong** — the AniList id is
`content_details.data_source_ref_id` (nullable, indexed). A content with NO AniList link is a
first-class citizen: `resolveOrCreateForExtension` creates it with `dataSourceId = null`
(`ContentResolver.kt:173-189`) — that's exactly the shape CS3-only content would have.

### 2.2 The chain: anime ↔ source ↔ episode ↔ video

The persisted chain (per content, Aniyomi era):

1. **anime ↔ source**: `main_entry` denormalizes the CURRENT extension link
   (`extension_id`, `source_id`, `anime_url` — kept for the hot
   `getMainEntryByExtension(extensionId, animeUrl)` lookup that "avoids a JOIN on every
   extension-source open", `content.sq:45-47`), while `content_details` holds the authoritative
   ext axis (`extension_type`, `extension_id TEXT`, `source_id`, `anime_url` + ext metadata).
   `ContentResolver.updateMainEntrySources` keeps both in sync inside one transaction.
2. **A SharedPreferences layer duplicates the source link, keyed by AniList id**:
   `details_source_link:<anilistId>` → `"$sourceId:$animeUrl"`
   (`DetailsViewModel.kt:101,2433,2447,2656,2765-2766,2857-2861`). This is D-199-era "source-link
   persistence": the details screen reads the pref first to re-open the last-used source. Unlink
   writes empty string (`DetailsViewModel.kt:2966-2969`). [verified] Note this pref is keyed by
   *anilistId* — meaningless for CS3-only content (§8.6).
3. **episodes are NOT persisted as source-agnostic rows** — they live in
   `data_cache_episode` keyed `(main_id, episode_number)` (AniList-enriched metadata cache) plus
   the episode lists are re-fetched from the extension on every details open. Episode *identity*
   for persistence is either the normalized `"${mainId}|%05d"` key (watch progress;
   `WatchScreen.kt:2115-2125`, `DetailsViewModel.kt:3051`) or the raw `SEpisode.url` (download
   queue + resolve registry; `DownloadModels.kt:52-58`). The raw list is normalized by
   **`EpisodeListNormalizer`** (D-313): dedupe by URL (first wins), then either keep the
   extension's own numbers when they're "usable" (finite, 0≤n≤100k, all distinct) or atomically
   renumber 1..N — D-317 orders renumbering season-by-season when names carry season tags
   (`EpisodeListNormalizer.kt:61-111`).
4. **video**: never persisted as content — `ResolvedVideosRegistry` is in-memory
   (doc 14 §7); only *downloads* persist a chosen video (`video_url`, `video_server`,
   `video_quality`, `video_audio`, `video_headers` JSON on `download_queue`) and the streaming
   cache persists an identity *hash* (§1.5).

### 2.3 (Re-)linking flows

- **auto-link** (`AutoLinkService`/`ReverseAutoLinkService`, doc 14 §8) and **manual link**
  (`DetailsViewModel.linkSource`, `:2857`) both end in `ContentResolver.linkExtensionToExisting` →
  `updateExtensionAxis` + `updateMainEntrySources` + `contentId` regeneration, one transaction.
- **unlink**: `clearExtensionAxis` nulls every `ext_*` column — the row survives with its library
  entries, watch progress, etc. (`content.sq:320-334`).
- **switch source**: `updateDownloadContentId` / `updateDownloadedContentId` (REVIEW-5 M7) keep
  queue + files rows pointed at the *current* content identity when the user switches
  (`downloadQueue.sq:136-141`, `downloadedEpisode.sq:119-123`).
- **re-link on reinstall**: `ContentResolver.resolveOrCreateForExtension` falls back to a
  contentId lookup when `(extensionId, animeUrl)` misses — "handles reinstall case where the
  scanner restored main_entry from data.json" (`ContentResolver.kt:139-154`).

### 2.4 Identity lifecycle walkthrough (what gets written, when)

The concrete write sequence for a title found via extension search and added to the library
(traced through `ContentResolver` + `DetailsViewModel` + stores):

1. **Search result tapped (extension path)** → `resolveOrCreateForExtension(extensionId,
   sourceId, animeUrl, title)` → INSERT `main_entry` (UUID mainId, contentId v1) + INSERT empty
   `content_details` row (D-206 guard so the follow-up axis UPDATE can't no-op)
   (`ContentResolver.kt:123-219`).
2. **Details load** → `updateExtensionAxis` fills `ext_*` (description/genres/status/thumbnail +
   `ext_extra_json`); if auto-link finds an AniList match → `linkAniList` → `updateDataSourceAxis`
   fills `data_*` + regenerates contentId in one transaction (`ContentResolver.kt:230-254`);
   `details_source_link:<anilistId>` pref written (`DetailsViewModel.kt:2433`).
3. **Episode list fetched** → `EpisodeListNormalizer` (D-313/D-317) → `data_cache_episode`
   upserts keyed `(main_id, episode_number)` + `content_genre` refresh.
4. **Added to library** → `library_item` row (Default category) — nothing else (progress is
   independent).
5. **Watched** → `watch_progress` upserts (key `"mainId|00001"`) + `activity_event` rows +
   on ≥85%: `completed=1` → AniList relay via `getHighestWatchedEpisodeNumber` → `track_entry`
   cache upsert after remote sync.
6. **Downloaded** → `download_queue` row (key `mainId + SEpisode.url`, resolve_context JSON) →
   on finish → `downloaded_episode` row + `data.json` written to the SAF folder (the durable
   record) → queue row purged after 10 s.
7. **Tracked in Updates feed** → `episode_update` row on each newly discovered episode;
   `anime_update_state` row when the anime enters the update engine; `episode_schedule` rows from
   the AniList schedule fetch.

Every step keys off `main_id` — which is why source switches (step 2 re-runs) never lose steps
4-7. This is the property the CS3 design must preserve (§8).

### 2.5 The `external_reference` story — plan vs reality

The Phase-2 plan (`17-database-schema.md:103-148`) designed an `external_reference(uid, ecosystem,
source_id, external_id, confidence, is_user_confirmed)` table **plus**
`episode_external_ref` (`:178-212`) with partial unique indexes per ecosystem — a genuinely
multi-source N-refs-per-content model. **None of it was built** (`18-phase3-plan.md:28`). What got
built instead (D-198) is the two-axis `content_details`, which supports **at most one data-source
link + one extension link per content**. Doc 14 §6.6's claim that the DB "is already
ecosystem-keyed" via `external_reference` is therefore a pointer to a *plan*, not code — the real
ecosystem-awareness is: the `system` lookup table (seeded with `cloudstream`,
`ContentRepository.kt:59-66`), the `extension_type` discriminator
(`'aniyomi'|'cloudstream'|'sora'|'mangayomi'`, `content.sq:84`), and the provider-api's
ecosystem-prefixed key strings (`"<ecosystemId>:<sourceId>:<externalId>"`, doc 14 §6.3) which were
"designed to feed" the never-built table. **Doc 17 (B4-b) must decide: revive the
external_reference design or extend the axis model** (§8.1).

## 3. Watch history & progress model

**Entities**: `watch_progress` (§1.4) is the whole story for position/state;
`activity_event` is analytics only; `PlaybackStateStore` (SharedPreferences, key prefix
`playback_state_<episodeKey>`, JSON of speed/subtitle/audio-track ids) keeps *player settings* per
episode (`PlaybackStateStore.kt:31-33,42-50`) — position/duration deliberately live in SQLDelight.

**Write path**: MPV player flushes `SqlDelightWatchProgressStore.save(episodeKey, progress)` every
10 s + on pause/dispose (`watch.sq:35-36` comment; `SqlDelightWatchProgressStore.kt:31-60`).

**The CF1 auto-mark state machine** (85% threshold, two flags — `SqlDelightWatchProgressStore.kt:38-60`):
- fraction > 0.85 AND not suppressed → `completed=1, completed_at=now` (auto-mark fires);
- rewind below threshold while completed → **stays completed** (auto-unwatch NEVER happens — IM9);
- user un-marks → `auto_mark_suppressed=1, completed=0` (must re-cross 85%); re-armed on next
  FILE_LOADED (`resetAutoMarkSuppressed`);
- user explicitly marks → `user_marked_watched=1` sticky;
- completion increments `watch_count` + backfills `first_watched_at`
  (`incrementWatchCount`, `watch.sq:80-84`).

**Resume**: `getContinueWatching` = `completed=0 AND auto_mark_suppressed=0 AND position>0 ORDER BY
last_watched_at DESC` served by the partial index (`watch.sq:61-65,29-31`). The Watch screen reads
the row for `"${mainId}|%05d"` and seeks. Episode watch states on the details page come from
`getWatchProgressByMainId`.

**Episode watch-state derivation** (details-page badges, from the two flags + completed):

| `completed` | `user_marked_watched` | `auto_mark_suppressed` | UI state |
|---|---|---|---|
| 0 | 0 | 0 | unwatched (in-progress if `position>0`) |
| 1 | 0 | 0 | watched (auto-marked at ≥85%) |
| 0 | 0 | 1 | user un-marked — suppressed until 85% re-crossed |
| 1 | 1 | — | watched (sticky manual) |

**Where "history" lives**: the History screen is a projection of `watch_progress` — HistoryViewModel
deletes via `watchProgressStore.delete`/`deleteAll` and enriches each row by parsing the episode
number out of the key (`substringAfterLast('|')`) + reading content_details for cover/title
(`anime-history/.../HistoryViewModel.kt:53-95`). The Profile's activity heatmap/timeline is ALSO
computed from watch_progress (`profile/ProfileViewModel.kt:154-158,267`); `activity_event` is a
write-heavy analytics log (inserted via `core/activity-tracker/ActivityTracker.kt:118` from
watch/details/search/download flows) whose read side is mostly retention pruning
[verified: many `insertEvent` callers; thin `getRecentEvents`/stats consumers].
`PlaybackStateStore` restores per-episode player settings (speed/track ids) next to the SQLDelight
position on resume (`PlaybackStateStore.kt:42-50`).

**AniList relay**: `getHighestWatchedEpisodeNumber` extracts the number after `|` in the key
(SQL string surgery — `watch.sq:114-121`) and `DetailsViewModel.relayWatchProgressIfNeeded`
pushes it as AniList progress (D-242-fix). Note this bakes the "global episode number" assumption
into the key format itself (§8.2).

## 4. Download model

### 4.1 Queue + files + the dual truth

**Enqueue path**: resolver flow (doc 14 §7) picks a video → `DownloadOrchestrator.buildRequest`
assembles `DownloadRequest` = `DownloadContentInfo` (mainId + aniyomi FK fields — carried for
data.json) + `DownloadEpisodeInfo` (episodeKey = `SEpisode.url`) + video context
(server/quality/audio/headers) + subtitle/audio tracks, and serializes the 7-field
`ResolveContext` into the row (`DownloadOrchestrator.kt:232-248`); `DownloadStore.insertTask`
writes the QUEUED row — the insert query hardcodes `state='QUEUED', progress=0, total_bytes=-1`
(`downloadQueue.sq:78-93`) and re-queries the `(main_id, episode_key)` UNIQUE tuple for the row id.

`download_queue` (active work) and `downloaded_episode` (finished files) are both re-keyed
`(main_id, episode_key)` (v2, D.0). The durable **source of truth for reinstall recognition is the
`data.json` file inside each SAF content folder** — the DB tables are a cache the
`DownloadScanner` reconciles at startup (`downloadedEpisode.sq:5-9`; `DownloadStore.kt:13-16`;
`ContentDataJson.kt:10-39` — carries contentId, FK fields, and the full episodes list with URIs).
`data.json`'s comment literally invokes §30: "per §30 debug-build schema freedom, we don't worry
about migration… clear app data → reinstall → fresh DB → test" (`ContentDataJson.kt:12-14`).

### 4.2 States

7-state machine on `download_queue.state` (`downloadQueue.sq:9-10`); crash recovery resets
DOWNLOADING/RETRYING→QUEUED at startup (`resetDownloadingToQueued`, `:165-171` — fixes the old
project's stuck-DOWNLOADING bug); retry metadata (`retry_attempt/max=3`, backoff via
`recent_ratios_json` moving average); terminal states purged (`purgeCancelled`,
`purgeCompleted` after 10 s auto-clear).

### 4.3 Resolve / re-resolve persistence (the proxy-churn fix)

Because aniyomi extensions serve videos through **localhost proxy URLs that die when the extension
process churns**, each queue row persists `resolve_context` — a JSON
`ResolveContext(sourceId: Long, episodeUrl, serverName, audioLabel, quality, mainId, episodeKey)`
(`ResolveContext.kt:24-33`; column `downloadQueue.sq:56-57`). On IOException,
`ReResolver.reResolve` re-resolves via the pinned (server, audio, quality) — a DIRECT lookup, it
never re-runs AutoDownloadEngine (REVIEW-5 M17) — and `updateDownloadVideoUrl` persists the fresh
localhost URL so pause/resume retries the new URL (`downloadQueue.sq:114-121`, D-149-fix). The
context's `sourceId: Long` + `episodeUrl` are **Aniyomi-shaped** — CS3's `loadLinks` needs
provider-name + content URL + `Episode.data` instead (§8.4).

### 4.4 Streaming cache (adjacent)

`playback_cache_entry`'s stable-identity-hash key (§1.5) is the *good* pattern to copy for any CS3
cache table: identity from (content, episode, source, server), never from volatile URLs.

## 7. Migration policy — the actual state

**The stated policy (CORE_RULES §30 "Debug-Build Schema Freedom")**: "The project is currently in
debug builds only… complete schema changes without migration concerns… Existing dev-install data
will be wiped — that's acceptable"; the user clarification: "we are NOT going to worry about
database migration. When the schema needs to change, we create new schema files and use them; the
old database is completely deleted and recreated… Do not invest time in `.sqm` migration files or
`user_version` tracking until the user explicitly signals production approach"
(`CORE_RULES.md:491-507`).

**The actual mechanism** [verified]:
- **No `.sqm` files exist; schema version is always 1.** SQLDelight derives the version from
  migration files — with none, `onUpgrade` is *never called* (old DB is also v1; 1==1 → no-op),
  which the driver comment explains in detail (`DatabaseDriverFactory.kt:19-27`).
- Instead, `onOpen` (runs every open) executes `migrateSchemaIfNeeded`: DROP dead tables, DROP +
  recreate `content`→`main_entry` via `onCreate(db)` re-run ("debug builds" per comment,
  `:87-99`), then **~30 idempotent `hasColumn`-guarded `ALTER TABLE ADD COLUMN`s** covering every
  schema drift since Phase WP (watch_progress cols, data_cache_episode cols incl. the 8 D-190
  metadata columns, download_queue episode_description, anime_update_state learned_offset_ms,
  playback_cache_entry session-2 cols), index drops/creates (Phase DB-OPT), a library_item dedup
  DELETE before adding the UNIQUE index, and `PRAGMA foreign_keys = ON` (`:36-305`; `hasColumn`
  helper `:310-329`).
- The rule itself calls this what it is: "acceptable as a lightweight runtime guard, but it is NOT
  a migration system" (`CORE_RULES.md:507`).

**Docs obligations** (CORE_RULES §24, `:373-404`): every table group should have a doc in
`DOCUMENTATION/database/` + a `changelog.md` for migrations. Current state: only `README.md`
(with an inline "Migration changelog" section) + `playback-cache.md` exist; the README itself
flags the rest as doc-debt (`DOCUMENTATION/database/README.md:3-14`). §30 supersedes §24's
migration-strictness while debug-only (`:501`).

**Implication for CS3 work**: Batch 4 may freely add tables/columns (or even reshape
`content_details`) with **no migration burden** — the only mandatory hygiene is (a) idempotent
`hasColumn`/`onCreate` guards so existing dev installs don't crash on open, and (b) the §24 doc +
§25 dashboard updates (§9).

### The 5 hardest schema problems for Batch 4 (ranked)

1. **Multi-source identity: single-slot extension axis → N links.** One `ext_*` axis + one
   denormalized `(extension_id, source_id, anime_url)` on `main_entry` can't hold "same show on
   provider A and B". Either revive `external_reference` (plan doc 17, §2.5) as
   `content_source_link(main_id, ecosystem, source_ref, url, is_preferred)` or accept
   single-active-source semantics for Cloud Screen v1. This decision cascades into content_id
   generation, re-link flows, and every "switch source" path (§2.3).
2. **Season-aware episode identity.** Add a season dimension to the persistent key space:
   `watch_progress.episode_key` format, `data_cache_episode` UNIQUE key, download episode keys,
   and the `E00001` file naming all assume one global 1..N numbering per title. CS3 TV series
   (multi-season, season-scoped numbers, unnumbered episodes → season 0, doc 05 §4.1-4.2) break
   the assumption. Must define ONE canonical normalization (e.g. global number derived
   season-by-season like D-317, persisted) or re-key everything `(main_id, season, episode)`.
3. **Ecosystem-typed resolution context.** `ResolveContext(sourceId: Long, episodeUrl, …)` +
   `ReResolver` + `playback_cache_entry.source_id/server_key` are aniyomi-shaped; CS3 needs
   `(providerName, contentUrl, Episode.data)` + `loadLinks`. Needs a polymorphic, serialized
   resolve context (add `ecosystem` discriminator) and a resolver dispatch — the persistence side
   of doc 14 §9's provider-bridge problem.
4. **Auxiliary engines keyed to the AniList data axis.** `anime_update_state` (airingAt, RELEASING,
   total_episodes), `episode_schedule`, `notification_config` semantics, tracker relay
   (`getHighestWatchedEpisodeNumber`), and the `details_source_link:<anilistId>` pref all assume
   an AniList link exists. CS3-only titles must either get a degraded mode (nullable-driven) or a
   parallel CS3 update path feeding the shared `episode_update` feed. Schema-wise: make AniList
   columns nullable *in spirit* (they mostly are) and add a CS3 poll-state table.
5. **`main_entry.extension_id INTEGER` + Long-typed source ids everywhere.** The denormalized hot
   column and all SharedPreferences source references (search-selected source, source link value)
   are Longs — CS3 providers have no numeric id (name + uuid). Schema-level fix is cheap
   (`extension_id` is already TEXT in `content_details`); the *ecosystem-qualified source key*
   (`"cloudstream:<providerName>"`) must replace bare Longs through prefs, the source registry,
   and UI models (mirrors doc 14 §9 seam 5).

## 9. Dashboard / tooling implications when CS3 content lands

1. **`lib/schema.ts` must be regenerated — it's already stale before any CS3 work** (§6.3: 26
   pre-D-198 tables vs 24 real). When Batch 4 adds tables (`content_source_link`? `cs3_*` caches?
   subscription state), the right move is a *transcription pass over all `.sq` files* (the file
   header documents this method, `schema.ts:2-5`) — ideally scripted [gap: no generator script
   exists; transcription is manual today, which is exactly how it drifted].
2. **`DATABASE.json` exports need zero changes** — `exportAsJson()` iterates `sqlite_master`, so
   new tables appear automatically (`DebugDatabaseBrowser.kt:208-213`). But its lossiness (§6.1)
   means any CS3 table with big JSON blobs (DTO caches) will export as
   `"<long text: N chars>"` — fine for structure review, useless for payload debugging. If Cloud
   Screen debugging needs payloads, raise the 4 KB `renderCell` limit or add a per-table raw mode.
3. **`/db-viewer` needs zero changes** (generic JSON explorer, §6.2) — the sample-DB fetch URL
   points at `DB.json` on GitHub main; whoever refreshes the root export must also push it there
   [inferred — the local file is `DATABASE.json`, the fetched one `DB.json`; a rename step exists
   somewhere in the manual pipeline].
4. **`/database-review` + `/database-plan` are historical** (D-198 analysis + plan). A CS3-era
   review page (or a section) should follow the same pattern: per-table MERGE/KEEP/DROP-style
   verdicts — the doc-15 §8 table above is the source material for it.
5. **§24/§25 obligations**: new tables need `DOCUMENTATION/database/<group>.md` entries + the
   README's inline migration-changelog updated (no `.sqm` exists to log, §7), and CORE_RULES §25
   requires the dashboard pages updated in the same task — the D-198 drift shows what happens when
   that's skipped.
6. **Debug-bubble DB tab**: free live browsing of new tables (`queryTable` is generic); the
   `DebugDbStats` per-table charts will automatically include CS3 tables once queried.
